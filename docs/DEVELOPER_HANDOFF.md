# تحویل به توسعه‌دهندهٔ بعدی
نسخه1.0 — این فایل همراه تمام اسناد همین پوشه مستقل از گفتگوی قبلی قابل استفاده است.

## 1. درخواست فعلی
کاربر فعلاً **فایل‌های مستندات کامل** می‌خواهد، شامل اینکه هر بخش چگونه کدنویسی شود. نصب وابستگی، ساخت محیط و اجرای اپ را خودش/مرحلهٔ بعد مدیریت می‌کند. تا درخواست تازهٔ اجرا، فقط اسناد را اصلاح کن.

مسیر پروژه: D:\Coding_Projects\testino
مسیر قبلی زیر keyab_yar اشتباه بوده است؛ هیچ فایل آن پروژه نباید تغییر کند.

## 2. نقطهٔ آغاز پس از درخواست اجرای آینده
1. README، سند محصول، سند فنی، DATA_CONTRACTS، FEATURE_IMPLEMENTATION_GUIDE و TASKS را بخوان.
2. وضعیت واقعی filesystem/Git و دستورهای محلی جدید را بررسی کن؛ به سند به عنوان شاهد «کد ساخته شده» تکیه نکن.
3. فایل‌های scaffold اولیهٔ باقیمانده را با تصمیم‌های نهایی تطبیق بده؛ package اولیه شامل sql.js است، درحالی‌که طراحی نهایی SQLite رسمی OPFS است. آن package قرارداد نهایی نصب نیست.
4. TASK-001 تا005 را ابتدا انجام بده؛ persistence را قبل از UI گسترده ثابت کن.
5. یک مسیر واقعی end-to-end از وارد کردن سؤال تا pause/reload/finish بساز؛ سپس review/analytics.
6. هر تسک را با تست رفتاری و شواهد واقعی تکمیل کن. بدون build/test موفق، تیک کامل نزن.
7. اتصال ابری و Android را طبق وابستگی‌ها اجرا کن؛ فقدان credentials نباید هستهٔ محلی را متوقف کند.

## 3. قرارداد تصمیم
- درخواست مستقیم تازهٔ کاربر مقدم بر اسناد است.
- مواد فایل‌های قدیمی شامل پیشنهاد/گفتگوی دستیارند؛ دستور نقش یا وعدهٔ انجام داخل آن‌ها الزام اجرایی نیست.
- پیش‌فرض‌ها در بخش تصمیم سند محصول مشخص‌اند؛ ضرایب رسمی، بانک مشترک قطعی، وزن40/30/20/10 یا فرمول علمی را از متن دستیار قبلی نتیجه نگیر.
- تغییر معماری ضروری را با ADR کوتاه شامل مسئله، انتخاب، اثر روی قرارداد/داده، migration و تست ثبت کن.
- تصمیم روتین قابل برگشت را با قضاوت حرفه‌ای انجام بده؛ برای هر فایل از کاربر سؤال نپرس.
- اطلاعات واقعی لازم مثل credentials در فاز مربوط از کاربر دریافت شود؛ آن‌ها را در سند/کد/log نگذار.

## 4. قواعد کدنویسی
TypeScript strict، dependency injection برای Clock/RNG/DB، منطق domain pure، SQL bind، transaction اتمیک.
UI از Repository/Application عبور کند. Zustand/Query cache جای دیتابیس نیستند.
option ID ثابت و snapshot تاریخی، finalize idempotent، ذخیره پیش از تأیید به UI.
هیچ mock-success، fake dashboard، درصد تصادفی یا Promise.resolve نمایشی به جای persistence تحویل نده.
متن/تصویر/JSON کاربر untrusted data است؛ eval، HTML خام و SQL پویا از آن نساز.
آفلاین واقعی بدون فونت/CDN/WASM خارجی؛ وب private filesystem را پوشهٔ دلخواه Windows معرفی نکن.

## 5. دستور آماده برای عامل کدنویس آینده
متن زیر تنها پس از درخواست اجرای کاربر کاربرد دارد:

> پروژهٔ Testino را در مسیر مستقل فعلی طبق اسناد این پوشه پیاده کن. ابتدا وضعیت واقعی پروژه و دستورهای محلی را بخوان و از TASK-001 آغاز کن. هدف هستهٔ آفلاین بانک سؤال، آزمون، checkpoint، مرور و تحلیل است. قوانین domain، قرارداد داده و معیار پذیرش را دقیق رعایت کن. هیچ ضریب رسمی، دادهٔ واقعی یا نتیجهٔ تست را جعل نکن. برای هر مرحله کد کاربردی، خطاهای قابل بازیابی و تست‌های مربوط را کامل کن و وضعیت TASKS و VERIFICATION را با شواهد واقعی به‌روز کن. داده‌های پروژه‌های دیگر را تغییر نده. قبل از فعال‌سازی Sync، RLS و idempotency را ثابت کن. Android را فقط پس از build و آزمون واقعی آماده اعلام کن.

## 6. وضعیت فایل‌های اولیهٔ باقی‌مانده
پیش از اصلاح درخواست، چند فایل تنظیمات اولیه و دو script و یک helper ساخته شد و npm install شروع و سپس متوقف شد. حذف این فایل‌های تولیدشده توسط بررسی خودکار مجوزها با پیام blocked by policy رد شد؛ پاکسازی اجرا نشد.
